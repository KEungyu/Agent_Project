# R1 — 시연 데이터 불러오기

## 동작

첫 화면 상단에 **시연 데이터 불러오기** 버튼이 표시된다. `MAIL_MODE`를 설정하지 않으면 앱은 모의 발송을 사용한다.
실제 모드는 기존 메일 설정이 모두 있고 시험 수신처가 정확히 1개일 때만 버튼을 표시한다.
누르면 영어로 된 새 여행을 만든다. 기존 보드·숙소·요청·회신·이벤트를 수정하거나
삭제하지 않으며, 기존 보드의 메모리 대화도 유지한다. 새 여행의 요청과 대화는 비어 있다.
예전 보드로 돌아가는 UI는 이번 변경에 포함하지 않는다.

- Emma Smith / DEMO-20261019 / Majungi Demo Hotel (Fictional)
- 모의 수신처: front@majungi-demo.test
- 실제 수신처: 서버 MAIL_ALLOWLIST의 유일한 주소. 개인 주소를 소스에 넣지 않는다.
- 입국: 2026-10-19 22:30 KST, ICN T2
- 체크인: 10/19, 체크아웃: 10/22, 숙소 도착: 10/20 01:30 KST
- 출국: 10/25 18:30 KST, ICN
- 일정: 10/19 서울 → 10/22 경주 → 10/23 부산

시연 버튼은 AI 호출·승인·발송을 하지 않는다. 저장 중 버튼을 잠그고,
서버에서 이전 보드 ID를 확인해 중복·오래된 화면의 요청을 거부한다.
저장 도중 실패하면 새 여행 전체를 롤백한다.
실제 모드의 설정 누락, 수신처가 여러 개이거나 잘못된 주소인 경우, `.test` 수신처,
잘못된 MAIL_MODE에서는 버튼을 숨기고 서버에서도 거부한다. 불러오기 자체는 발송하지 않는다.

## 실행

```sh
MAIL_MODE=mock DATABASE_FILE=data/demo-button-qa.db OUTBOX_DIR=data/demo-button-outbox npm run dev -- --webpack --hostname 127.0.0.1 --port 3107
```

실제 AI 생성은 기존 설정대로 프로젝트의 로컬 환경 파일에 GEMINI_API_KEY 또는
ANTHROPIC_API_KEY가 있어야 한다. 키 값은 공유 자료나 저장소에 넣지 않는다.

1. 오프닝을 닫고 **시연 데이터 불러오기**를 누른다.
2. Emma Smith, 예약번호, 늦은 도착 알림, 빈 요청 목록, 모의 모드 표시를 확인한다.
3. 채팅에 아래 요청을 입력하고 한국어 초안·영어 번역·수신처를 확인한다.

> Please ask my hotel whether I can check in at 1:30 AM on October 20, 2026, Korea time. My reservation starts on October 19. Use the booking details on my trip board and show me the Korean email and English translation before sending.

4. **Approve (demo send)**를 누르고 **Demo mode: not actually delivered**를 확인한다.
5. 아래 가상 회신을 붙여 넣고 **What does it say?**를 누른다.

> 안녕하세요, Emma Smith 고객님. 예약번호 DEMO-20261019의 10월 19일 체크인 예약을 확인했습니다. 10월 19일 22시까지 온라인 체크인을 완료하시면 10월 20일 오전 1시 30분에 입실하실 수 있습니다. 온라인 체크인 완료 후 출입 방법을 안내드리겠습니다.

6. 조건부 수락, 10/19 22:00 온라인 체크인 기한, 조건 미확인 시 완료 버튼 비활성화를 확인한다.
7. 다시 시작할 때 버튼을 누르면 직전 요청·회신은 이전 보드에 보존된다.

## 운영 범위

- 앱은 전역 최신 보드를 공유한다. 시연 중 다른 접속에서 여행을 만들거나 버튼을 누르지 않도록 맞춘다.
- 날짜는 이번 2026년 10월 발표용이다. 10월 20일 이후 다시 시연한다면 초안·회신 예문과 함께 갱신한다.
- 기존 데이터 보존은 버튼 동작에 대한 보장이다. 무료 Render의 임시 디스크는 재배포·재시작 시 초기화될 수 있으므로 기록을 유지하려면 배포 전 별도 백업이 필요하다.
- 서버 기동 대기와 AI 지연은 이 버튼으로 해결되지 않는다.


## 실제 메일 시연 연결

1. 실행할 프로젝트의 `.env`에 `GEMINI_API_KEY` 또는 `ANTHROPIC_API_KEY`를 설정한다.
2. 같은 환경에 `RESEND_API_KEY`, `MAIL_FROM`, `MAIL_ALLOWLIST`를 설정한다. 허용 목록에는 팀 소유 시험 수신 주소 1개만 넣는다.
3. `MAIL_FROM`은 Resend에서 사용할 수 있는 발신 주소여야 한다. 기본 시험 도메인은 계정 소유자 주소로만 보낼 수 있고, 다른 수신처를 쓰려면 검증된 도메인의 발신 주소가 필요하다. Gmail 수신 주소를 그대로 발신 주소로 지정하지 않는다. [Resend 공식 오류 안내](https://resend.com/docs/api-reference/errors)
4. `MAIL_MODE=real`로 변경 후 서버를 다시 시작한다. 버튼 아래 실제 메일 안내를 확인한다.
5. 시연 데이터를 불러온다. 아래 문장을 기존 영문 요청 뒤에 추가한다.

> This is a fictional demonstration. Start the Korean email subject with [마중이 시연 테스트] and say in the body that this is a fictional demo booking. Show me the exact Korean email and English translation before sending.

6. 승인 카드에서 수신처·제목·본문을 확인하고 **Approve and send**를 누른다. 서비스 접수는 받은편지함 도착과 다르다.
7. Gmail에서 제목과 수신 시각으로 해당 메일 1건을 찾아 본문을 확인한다. 결과가 불명확하면 새 요청을 만들어 재발송하지 말고 기존 기록과 받은편지함부터 확인한다.
8. 회신 해석 시연은 위의 가상 회신을 붙여 넣는다. 현재 앱은 Gmail 회신을 자동으로 가져오지 않는다.

설정이 어려우면 기존 **Open in my email app** 버튼으로 사용자가 직접 보내는 경로도 가능하다. 이 경우 발표에서 수동 발송임을 밝히고, 앱의 자동 발송 완료로 설명하지 않는다.

## Render 배포 담당자 확인 순서

1. **재배포 전에 저장소 확인.** 저장소의 `render.yaml`은 Free 서비스와 로컬 SQLite를 사용한다. 실제 대시보드의 플랜, `DATABASE_FILE`, 영구 저장소·백업 유무를 확인한다. 기존 데이터의 보존 방안을 확보하거나 담당자가 시연 기록 초기화를 명시적으로 허용한 뒤에 환경변경에 따른 재시작이나 병합·배포를 진행한다. 최신 보드가 비어 있어도 과거 기록이 없다는 증거는 아니다.
2. Free 서비스에서는 재배포·재시작·휴면 시 로컬 파일이 사라지며 Shell/SSH도 제공되지 않는다. 현재 실행본에는 DB 전체 내보내기 기능이 없다. 따라서 Free 서비스에 접속해 백업 명령만 실행하면 된다고 가정하지 않는다. 기록을 유지해야 한다면 보존 대상과 실제 복구 가능한 백업을 먼저 확인한다. [Render 공식 안내](https://render.com/docs/free)
3. 서비스의 Environment에 기존 AI 키를 유지하고, 위의 `RESEND_API_KEY`, `MAIL_FROM`, 팀 소유 수신 주소 1개를 담은 `MAIL_ALLOWLIST`, `MAIL_MODE=real`을 설정한다. 키와 개인 주소는 GitHub에 게시하지 않는다. 저장·재배포는 1번이 해결된 뒤 진행한다.
4. `render.yaml`은 `MAIL_MODE`를 `sync: false`로 선언한다. 기존 Blueprint의 동기화는 이 항목을 건드리지 않으므로 값은 서비스의 Environment에서 직접 관리한다. 새 Blueprint 생성 시에는 값을 입력하며, 실제 발송 준비 전에는 `mock`을 사용한다. 앱은 값이 없을 때 모의 발송을 사용한다. [Render 환경변수 동기화 규칙](https://render.com/docs/blueprint-spec#prompting-for-secret-values)
5. 변경 PR을 검토·병합하고 Render가 해당 커밋을 배포했는지 확인한다. 설정 저장만으로 최신 코드가 반영됐다고 판단하지 않는다.
6. 공개 사이트에서 버튼과 실제 메일 안내를 확인하고, 위의 실제 메일 시연 절차를 한 번 실행한다. 실제 AI 초안, 승인 후 메일 서비스 접수, Gmail 실수신, 붙여넣은 회신의 실제 AI 해석을 각각 기록한다. Gmail 자동 회신 수집은 구현 범위에 포함되지 않는다.
