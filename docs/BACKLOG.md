# 마중 — 구현 백로그

> 관련 문서: [PRD.md](PRD.md), [ARCHITECTURE.md](ARCHITECTURE.md), 작업 규칙 [../AGENTS.md](../AGENTS.md)
> 기술 스택이 정해지기 전까지 완료 기준의 "실행 명령"은 자리표시자다. M0에서 실제 명령을 README에 적고 이후 단계는 그 명령을 쓴다.

## 읽는 법

- **한 단계 = 반나절~하루.** 에이전트(코딩 도구)에는 한 번에 한 단계만 지시한다 (AGENTS.md 규칙 1).
- **담당**: A = 앱 골격·저장소·상태 머신·UI·발송 / B = LLM·프롬프트·도구·해석·평가. 제안일 뿐이고 팀 사정에 맞게 바꾼다.
- **브랜치**: `<종류>/<단계ID>-<짧은-이름>`. 종류는 `chore`, `feat`, `test`, `docs`, `release`. `main`에서 따고, 완료 기준을 통과하면 PR로 합친다.
- **완료 기준**은 명령 실행이나 화면 조작으로 확인할 수 있는 문장이다. 통과하지 못하면 다음 단계로 넘어가지 않는다.
- **픽스처(테스트 데이터)**: 예약 메일과 회신은 모두 팀이 작성한 가상 데이터다. 실제 업체 주소나 개인정보를 쓰지 않는다.

## 병렬 작업 계약

A와 B가 부딪히지 않도록 D1에 다음 두 가지를 먼저 고정한다. 고정한 뒤 바꾸려면 두 사람 모두 확인한다.
1. **보드·요청 데이터 모델** (ARCHITECTURE §4) — M2에서 A가 구현, B는 그 타입만 가져다 쓴다.
2. **요청 유형 스키마** (ARCHITECTURE §6) — M1에서 B가 구현, A는 로더 결과만 쓴다.

## 1부. MVP — 늦은 체크인 문의가 끝까지 동작

### M0. 스택 확정 반영과 프로젝트 골격
- **담당** A · **브랜치** `chore/m0-scaffold` · **분량** 반나절 · **선행** 팀의 스택 선택
- **작업**: 저장소 초기화(`git init`은 팀원이 직접), 선택한 스택의 최소 프로젝트, `.gitignore`(`.env` 포함), `.env.example`(키 이름만), README에 실행·테스트 명령 기록
- **완료 기준**
  - README의 실행 명령 하나로 로컬에서 "마중" 제목이 있는 빈 화면이 열린다.
  - `.env`를 만든 뒤 `git status`를 실행하면 `.env`가 목록에 나오지 않는다.
  - README의 테스트 명령을 실행하면 샘플 테스트 1개가 통과한다.

### M1. 요청 유형 스키마와 로더

- **완료 기준**

  - `required_slots`를 뺀 테스트용 파일을 넣고 실행하면 어떤 파일의 어떤 필드가 빠졌는지 출력하며 실패한다.

### M3. LLM 호출과 에이전트 루프 골격
- **담당** B · **브랜치** `feat/m3-agent-loop` · **분량** 1일 · **선행** M0, M2

  - 항상 실패하는 테스트용 도구로 실행하면 2회 실패 뒤 루프가 멈추고 종료 사유 `tool_error`가 출력된다.
  - `.env`에 키가 없으면 키 이름을 알려주는 오류를 내고 종료한다 (키 값은 출력하지 않는다).

  - 배지 3종이 서로 다른 모양으로 표시되고, "확정" 배지는 없다.
  - 채팅 입력이 M3 루프로 전달되어 답이 화면에 나온다 (M3 병합 후 확인).

### M5. 예약 정보 추출 도구 `extract_booking_info`

  - 추출 후 저장소를 조회하면 예약 메일 원문이 어디에도 저장되어 있지 않다.

  - 답한 뒤 같은 요청을 다시 시작하면 질문 없이 다음 단계로 넘어가고, `re_ask` 이벤트는 0건이다.

### M9. 승인 화면과 모의 발송 `request_approval` · `send_email`

- **완료 기준**

  - 승인하면 outbox에 메일 1건이 생기고 상태가 `발송됨 → 회신 대기`로 바뀐다.
  - 승인 후 본문을 한 글자 바꾸고 발송하면 해시 불일치로 거부되고 재승인을 요구한다.
  - 실제 메일 서버로는 아무것도 나가지 않는다 (모의 모드 로그 확인).

### M10. 회신 해석 `ingest_reply` · `interpret_reply`와 정확도 평가
- **담당** B · **브랜치** `feat/m10-reply-interpret` · **분량** 1일 · **선행** M8
- **작업**: 회신 4분류(완료/조건부 수락/거절/추가 정보 요청), 조건·요구 정보 추출, 이용자 언어 요약, 신뢰도 0.7 미만이면 `needs_user_check`, 정답 라벨이 붙은 가상 회신 20개(분류별 5개), 평가 명령
- **완료 기준**
  - 평가 명령을 실행하면 20개 샘플의 예측·정답 표와 정확도가 출력되고, 정확도가 85% 이상(17/20)이다.
  - 조건부 수락 샘플에서 조건(예: "도어락 비밀번호 당일 안내")이 `conditions`에 추출된다.

### M11. 회신 입력 화면과 해석 결과 카드
- **담당** A · **브랜치** `feat/m11-reply-ui` · **분량** 반나절 · **선행** M9, M10
- **작업**: 시연용 회신 붙여넣기·샘플 선택 화면, 해석 결과 카드(분류, 조건, 이용자 언어 요약, 원문 펼쳐보기), `needs_user_check`이면 분류 확인 버튼
- **완료 기준**

  - 신뢰도가 낮은 샘플을 넣으면 상태가 바뀌지 않고 확인 버튼이 나타나며, 확인을 누르면 상태가 바뀐다.

### M12. 채널 판단과 전화 스크립트 `decide_channel` · `make_phone_script`
- **담당** A · **브랜치** `feat/m12-channel-phone` · **분량** 반나절 · **선행** M8
- **작업**: `channel_rule`에 따른 채널 판단(`now`를 입력으로 받음), 한국어 전화 스크립트 + 발음 표기 + 예상 응답, 스크립트 화면
- **완료 기준**
  - `now`를 도착 30시간 전으로 주면 `email`, 3시간 전으로 주면 `phone`과 사유가 출력된다.
  - 전화 채널일 때 한국어 문장, 발음 표기, 예상 응답 3개 이상이 담긴 스크립트가 화면에 나온다.
  - 숙소 이메일이 없고 전화번호만 있으면 시간과 관계없이 `phone`이 나온다.

### M13. 후속 제안 `propose_next`
- **담당** B · **브랜치** `feat/m13-followup` · **분량** 반나절 · **선행** M10
- **작업**: 분류별 `follow_ups` 실행. 후속 초안은 `round+1`로 다시 승인 흐름을 탄다. 거절이면 대안 요청을 `parent_request_id`로 연결
- **완료 기준**
  - 추가 정보 요청 샘플을 넣으면 요구 정보가 채워진 후속 초안이 `round = 2`, 상태 `승인 대기`로 만들어진다.
  - 조건부 수락 샘플에서 이용자가 "수락"을 고르면 상태가 `완료`가 된다.
  - 거절 샘플을 넣으면 대안 제안(전화 스크립트 또는 이용자 선택)이 나오고, 대안을 고르면 새 요청이 원 요청과 연결된다.

### M14. MVP 통합 시나리오
- **담당** A+B · **브랜치** `test/m14-mvp-e2e` · **분량** 1일 · **선행** M0~M13
- **작업**: PRD §5 시나리오를 처음부터 끝까지 연결, 시연 데이터 초기화 명령, 버그 수정(범위 안에서만)
- **완료 기준**: 초기화 명령 후 화면 조작만으로 아래 세 시나리오를 재현할 수 있다.
