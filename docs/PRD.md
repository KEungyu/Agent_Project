## 1. 문제 정의

한국어를 못하고 한국이 처음인 단기 방문자는 **숙소·식당·교통 업체와 한국어로 소통해야 하는 순간**에 막힌다.

- **정보는 많지만 실행이 끊긴다.** 검색하면 "호텔에 늦은 체크인을 미리 알리세요"라는 조언은 나오지만, 연락처 찾기 → 한국어 작성 → 발송 → 회신 해석까지는 이용자 혼자 해야 한다.
- **도구가 흩어져 있다.** 메일 앱, 예약 앱, 번역 앱, 지도 앱을 오가면서 같은 정보(예약번호, 도착 시각)를 매번 다시 찾고 입력한다.
- **번역 결과를 검증할 수 없다.** 내가 보낸 한국어가 정확한지, 받은 회신에 조건(추가 요금, 비밀번호 안내 등)이 숨어 있는지 판단하기 어렵다.
- **챙겨야 할 일을 모른다.** 새벽 도착인데 체크인 확인을 안 했거나 다음 날 도시 이동편이 없다는 사실을 문제가 생긴 뒤에야 안다.

**마중의 답:** 정보를 알려주는 챗봇이 아니라, 목표를 받으면 *조건 확인 → 도구 선택 → 실행 → 결과 관찰 → 다음 행동 결정*을 반복하는 **에이전트**다. 모든 기능은 하나의 **"내 여행 보드"**를 읽고 쓰며, 보드를 점검해 빠진 일을 **먼저** 알려 준다.

### 범위 경계
- 대상: 여행·출장·연수·행사 참가·환승으로 오는 **단기 방문자**
- 범위 밖: 비자, 외국인등록 같은 **행정 업무** → 범위 밖이라고 알리고 공식 창구(1345 외국인종합안내센터)를 안내
- 핵심 약속: "다 대신 예약해 준다"가 아니라 **"끝까지 챙기고, 할 수 있는 건 대신 보낸다."**

## 3. 목표와 비목표

### 목표 (이번 과제)
1. **늦은 체크인 문의를 끝까지 대행한다.** 조건 확인부터 회신 해석과 후속 제안까지, 이용자는 입력·승인·선택만 한다.
2. **같은 조건을 두 번 묻지 않는다.** 보드에 있는 값은 다시 질문하지 않는다.
3. **먼저 챙겨준다.** 보드를 점검해 빠진 일을 이용자가 묻기 전에 알린다.
4. **정직하게 표시한다.** 모든 기능에 실행 단계 배지(안내 / 준비 / 대행)를 붙인다.
5. **새 요청 유형을 데이터로 붙인다.** 늦은 체크인 다음 유형(예: 짐 보관)을 코드 수정 없이 설정 추가만으로 동작시킨다.
6. **AI 적용 전/후 차이를 수치로 보여준다.** 모든 상태 변경을 시각과 함께 기록해 지표를 산출한다.

### 비목표
| 비목표 | 이유 |
|---|---|
| **확정** 단계(결제·본인인증을 포함한 예약 완료) | 결제, 본인인증, 공식 연동이 필요하다. 화면에 "확정" 배지를 쓰지 않는다 |
| 비자·외국인등록 등 행정 업무 | 범위 밖이다. 1345로 안내한다 |
| 긴급 상황 대행(신고, 전화 걸기) | 공식 번호(112, 119, 1330)를 먼저 보여주고 앱이 대신하지 않는다 |
| 앱이 직접 전화 걸기 | 채널 판단 결과가 전화이면 스크립트와 발음만 제시한다 |
| 개발·시연 중 실제 업체로 발송 | 모의 발송만 한다 (컨셉 6장) |
| 이용자 승인 없는 외부 발송 | 안전 원칙. 모든 외부 발송은 승인 후에만 한다 |
| 로그인·다중 사용자·다중 여행 관리 | 10일 범위를 넘는다. 이용자 1명이 여행 보드 1개를 쓰는 것으로 가정한다 |

## 5. AI 적용 전/후 workflow — 늦은 체크인 문의

**시나리오:** Emma가 00:40 인천공항에 도착해 서울 숙소에 01:30쯤 도착할 예정이다. 숙소에 늦은 체크인이 가능한지, 출입 방법이 무엇인지 확인하려 한다. 첫 회신은 "가능하지만 프런트가 24시에 닫으니 도어락 비밀번호를 당일 메일로 보내겠다"는 **조건부 수락**이다.

> ⚠️ 아래 소요 시간은 모두 **예상치**다. 업체의 회신을 기다리는 시간은 양쪽 모두 제외하고, 이용자가 직접 손을 쓰는 시간만 셌다. 실측값은 P1 리허설에서 같은 시나리오로 측정해 교체한다.

### 5-1. AI 적용 전

| # | 단계 | 행위자 | 사용 도구 | 예상 소요 (예상치) |
|---|---|---|---|---|
| 1 | 예약 확인 메일·앱에서 숙소 연락처와 예약번호 찾기 | 이용자 | 메일 앱, OTA 예약 앱 | 5분 |
| 2 | 연락 방법 결정 (OTA 메시지 / 메일 / 전화), 체크인 정책 확인 | 이용자 | OTA 앱, 웹 브라우저 | 5분 |

### 5-2. AI 적용 후 (마중)

| # | 단계 | 행위자 | 사용 도구 (마중 내부) | 예상 소요 (예상치) |

| 2 | 보드 조회 → 필수 조건 대조 → **빠진 것만** 질문 | 에이전트 (+이용자 답변) | `board_get`, `check_conditions`, `ask_user` | 수 초 (+이용자 1분) |
| 3 | 예약 정보에서 숙소 연락처·예약번호 추출 → 보드 저장 | 에이전트 | `extract_booking_info`, `board_update` | 수 초 |
| 4 | 채널 판단 (도착까지 6시간 이상이면 메일) | 에이전트 | `decide_channel` | 수 초 |
| 5 | 한국어 요청문 + 이용자 언어 역번역 작성 | 에이전트 | `draft_request_ko`, `back_translate` | 10~20초 |
| 6 | 원문과 역번역을 나란히 확인하고 **승인** | 이용자 | 승인 화면 | 1분 |
| 7 | 발송 (시연 중에는 모의 발송) → 상태 기록 | 에이전트 | `send_email` | 수 초 |
| 8 | 회신 해석 → "조건부 수락" 분류 → 이용자 언어로 요약 | 에이전트 (+이용자 확인) | `interpret_reply` | 수 초 (+이용자 1분) |
| 9 | 후속 회신 초안 제안 → 승인 → 발송 | 에이전트 + 이용자 승인 | `propose_next` → 5~7 재사용 | 2분 |
| | **합계** | 이용자는 입력·승인·확인만 | 마중 1개 | **약 7분** |

### 5-3. 전/후 요약 (예상치)

| 지표 | 적용 전 | 적용 후 | 비고 |
|---|---|---|---|
| 이용자가 직접 수행하는 단계 수 | 9 | 4 (입력, 답변, 승인, 확인) | 에이전트 단계는 제외 |
| 이용자 능동 소요 시간 | 약 58분 | 약 7분 | 회신 대기 시간 제외 |
| 도구·앱 전환 횟수 | 약 10회 | 0~1회 | 마중 밖으로 나가지 않음 |
| 같은 정보 재입력·재질문 | 3회 이상 (예약번호 등) | 0회 목표 | 보드 재사용 |
| 회신 해석 | 이용자 추측 | 4분류 + 조건 추출 | 정확도는 §6에서 측정 |

## 6. 측정 지표

모든 요청 상태 변경과 이용자 조작은 **시각과 함께 이벤트로 기록**한다 (ARCHITECTURE §4 `events`).

| 지표 | 정의 | 측정 방법 | 목표 (가정) |
|---|---|---|---|
| 처리 단계 수 | 요청 1건을 완료할 때까지 **이용자가 직접 수행한** 조작 수 | `user_action` 이벤트 개수 | 적용 전 대비 50% 이상 감소 |
| 소요 시간 | 이용자 능동 시간 합계. 회신 대기는 제외 | 화면 진입부터 해당 단계 완료까지 시각 차의 합 | 10분 이내 |
| 도구 전환 횟수 | 처리 중 다른 앱·사이트로 이동한 횟수 | 적용 전: 리허설 관찰 기록 / 적용 후: 외부 링크 클릭 이벤트 | 1회 이하 |
| 재문의 횟수 | (a) 이용자에게 보드에 이미 있는 값을 다시 물은 횟수 (b) 같은 건으로 업체에 다시 연락한 횟수 | (a) `ask_user` 항목 중 보드에 값이 있던 경우 (b) `round` ≥ 2인 발송 수 | (a) 0회 (b) 해석 오류로 인한 재발송 0회 |
| 회신 해석 정확도 | 회신 분류(완료/조건부 수락/거절/추가 정보 요청)가 정답과 일치하는 비율 | 팀이 작성한 **가상 회신 샘플 20개**(유형별 5개)에 정답 라벨을 붙여 평가 | 85% 이상 |

> 적용 전 수치는 §5-1의 예상치로 시작하고, 리허설에서 팀원이 실제로 수행해 본 값으로 교체한다. 회신 샘플은 실제 업체 메일이 아니라 팀이 작성한 가상 데이터다.

## 8. 추가 제안 (범위 밖 아이디어 — 채택 전까지 구현하지 않음)

- **보드 초기화·내보내기 버튼**: 시연이 끝난 뒤 개인정보를 이용자가 직접 지울 수 있게 한다.
- **요청 취소 상태**: 승인 대기 중 이용자가 요청 자체를 그만두는 경로. 현재 상태 머신에는 없다.
- **업체 응답 템플릿 학습**: 자주 오는 회신 표현을 모아 해석 정확도를 높인다.
- **팀원 간 "시연 모드" 토글**: 현재 시각을 가상으로 바꿔 먼저 챙겨주기 규칙과 채널 판단을 시연한다.
- **VectorDB 검색**: TourAPI 데이터를 임베딩해 "마중이랑 상의하기"에 활용한다 (교수님 구두 메모 연결).

## 9. 2026-10-04 2차 피드백으로 넓힌 범위

팀이 받은 2차 피드백(예약·공항·이동 10개 항목)을 반영해 범위를 넓혔다. 실행 단계 배지와 비목표(확정·결제·실제 발송·앱의 전화 걸기)는 그대로다. "연결"은 예약이 아니고, "조회"는 이동 완료가 아니다.
